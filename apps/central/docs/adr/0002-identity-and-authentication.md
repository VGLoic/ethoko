# Multi-method identity, device-flow + PAT authentication, opaque tokens

A **User** can attach multiple auth methods (email + password, GitHub OAuth) to one persistent identity, independently of their optional **Handle Registration**. Linking only happens from an already-authenticated session; sign-in flows never silently merge accounts, and a GitHub sign-up whose email collides with an existing User is refused (mitigates account takeover via unverified email match — same posture GitHub.com uses). The CLI authenticates via OAuth 2.0 Device Authorization Grant (RFC 8628) for interactive sessions and via Personal Access Tokens for CI / headless use. Both produce **opaque tokens**, validated through one server-side hashed-lookup path. Email verification is OTP-based, gates write and security-sensitive operations (publish, mint PAT, link GitHub, change Visibility), but does not gate sign-in or handle registration; emails reported as `verified` by GitHub's `/user/emails` API are honored without an additional OTP step.

## Current OTP Request per purpose

An OTP Request is generic: both `email_verification` and `password_reset` purposes remain supported by the model. Database uniqueness on `(user_id, purpose)` permits one request of each purpose on the same User. Email-verification lookup, cooldown checks, replacement, and verification select only `email_verification`; another purpose cannot block, replace, or satisfy it.

Code assignment is explicit: `Unfilled` has no hash, while `Filled` carries a 32-byte hash. Persistence derives assignment from the nullable hash and constrains its length, avoiding contradictory state/hash combinations. Consumption remains independent. Verification checks already-verified, consumed, and expired conditions as before, then requires Filled before comparing a hash; a current, unexpired Unfilled request returns the existing invalid-OTP response.

Request creation locks the persistent User before checking verified-email state and purpose-scoped cooldown, including first creation when there is no request row to lock. After cooldown, a transaction deletes the previous request for that purpose and inserts a fresh Unfilled request identity, creation time, and expiration, with `consumed_at` unset. Timestamps are measured after acquiring the lock, not at transaction start. No historical rows are retained. Expired and consumed requests remain until replacement and are rejected at verification without a cleanup worker. Existing durations and rate limits are unchanged.

Verification takes the same User lock before reading the verified-email state and current email-verification request. It atomically marks the User's email verified and sets that request's `consumed_at`. If replacement commits first, the old code is invalid; if verification commits first, issuance rejects the already-verified User. Concurrent verification attempts cannot both succeed. Repeated verification retains its existing already-verified error, and further email-verification issuance remains forbidden. The latest retained request is not request history, even when consumed or expired.

The OTP Request creation migration is edited in place for a fresh database; no backfill or upgrade path is provided. It permits absent hashes and constrains present hashes to 32 bytes. HTTP integration tests exercise initial issuance, invalid, expired and superseded codes, renewed lifetimes and cooldowns, reuse rejection, already-verified resend rejection, concurrent verification, and verification racing replacement through the existing worker and captured emails. Consumption is observed through rejection of reuse, not exposed timestamps or persistence assertions. With no password-reset HTTP flow, per-purpose isolation and row cardinality are schema/code invariants not directly asserted through this HTTP-only seam; no lower-level tests or test-only endpoints are introduced.

### Signup and resend: synchronous creation, guarded background filling

Email signup inserts an Unfilled request in the same transaction as the User and password credential ([#227](https://github.com/VGLoic/ethoko/issues/227), following [#225](https://github.com/VGLoic/ethoko/issues/225)). Insertion failure rolls back all three. Creation starts expiry and cooldown; the synchronous service generates no code. After commit, the notifier best-effort enqueues metadata linking the User, exact request identity, and recipient, never a cleartext code. Enqueue failure is logged without failing committed signup: the request remains Unfilled and cooldown still applies. Recovery is a later resend after cooldown, not a promise of durable delivery.

Resend uses the same linked filling mechanism ([#228](https://github.com/VGLoic/ethoko/issues/228)). The service initiates replacement in the locked repository transaction before enqueueing or returning; preliminary User lookup is not authoritative for eligibility. Replacement commit immediately invalidates the old code, even before worker execution. Concurrent resends receive synchronous cooldown rejection rather than both succeeding and leaving rejection to a worker. Enqueue failure still returns success: the old code stays invalid, the new Unfilled request retains its lifetime/cooldown, and a later resend after cooldown can recover. An Unfilled request cannot verify any code.

Each linked worker attempt generates a fresh code in memory and invokes a dedicated authentication-service operation backed by the repository. Its transaction takes the shared persistent User lock and atomically requires an existing unverified User and the exact current email-verification request, unexpired and unconsumed. Time is measured after lock acquisition. Both Unfilled-to-Filled and Filled-to-Filled assignment are permitted. Assignment changes only the hash, preserving identity, purpose, creation time, expiry, and consumption; it never checks cooldown. Missing, replaced, expired, consumed, or already-verified work completes without sending or retrying. Unexpected persistence failure propagates to queue retries without sending.

Assignment commits before sending ([#219](https://github.com/VGLoic/ethoko/issues/219)). Sending failure uses existing queue retries, which regenerate the code and replace the same request's hash even inside cooldown. No delivery-status fields or post-send request mutations are introduced. Only the latest assigned hash is authoritative: a retry may invalidate an already-emailed code after an ambiguous send or acknowledgment failure. Overlapping attempts, duplicate or out-of-order emails, and the assignment/send race are accepted. No database lock is held during sending; replacement, consumption, or expiry may occur before delivery. Queue delay consumes the original lifetime and may leave no time for delivery at all. Codes are not logged; OTP debug formatting is redacted.

HTTP integration tests use the real database, controlled worker and captured emails to cover Unfilled rejection, pre-processing cooldown and old-code invalidation, concurrent resend rejection, successful filling and verification, expiry before processing, stale-request skips before and after replacement filling, consumed/verified skips, enqueue failure and recovery, and fresh-code retry after sending failure without renewing lifetime/cooldown. Verification/replacement and filling/replacement/verification races assert committed outcomes without promising race-free email delivery. Pure database failures are not injected; creation rollback and unexpected assignment-failure handling are not directly exercised by this suite.

### GitHub signup

New GitHub Users with unverified email receive an Unfilled email-verification request in the existing User-and-GitHub-credential transaction ([#229](https://github.com/VGLoic/ethoko/issues/229)). Insertion failure rolls back identity, credential, and request together. The repository returns persisted request metadata and never generates a code or enqueues work. After commit and session-token recording, the service best-effort notifies with the exact request identity, using the same guarded background filling operation as email signup and resend. Enqueue failure leaves authentication successful, the request Unfilled, and its original expiry/cooldown in force; a later resend can recover. Worker delay consumes the request lifetime, and expired or replaced signup work cannot create or fill a replacement request.

GitHub-verified signup and existing GitHub Users signing in create no request or delivery job through these flows. Existing unverified Users keep their current request/code on login, even after cooldown. OAuth transaction finalization and session-token recording retain their separate transaction boundaries; identity-collision rules, Suggested Handle, and Handle Registration behavior are unchanged. HTTP integration coverage includes these skips, unverified signup's pre-filling rejection/cooldown and captured-code verification, expired and obsolete work, and successful session authentication after enqueue failure followed by resend recovery. The harness has no request-insertion failure control, so rollback is enforced by the transaction but not directly failure-injected.

All email-verification entry points now create requests synchronously ([#230](https://github.com/VGLoic/ethoko/issues/230)). The worker depends only on the authentication service and email sender, with no request-creation repository or cooldown configuration. Request creation accepts no hash and always creates Unfilled requests; only guarded filling assigns a hash. The transitional worker-side creation job and its payload are removed. Previously retained jobs using that obsolete payload are no longer supported: deserialization fails through normal queue failure/retry handling, without creating a request or sending email. There is no compatibility fallback that can replace a current request.

Queue interfaces, retry configuration, retention, rate limits, and public responses remain unchanged. Enqueueing is not transactional with request creation; there is no outbox or durable code-bearing job payload. See [the asynchronous work queue decision](0003-async-work-queue.md).

## User and Handle Registration contract

The domain has one User entity and an optional Handle Registration identified by that User. Registration presence is authoritative; no User lifecycle is persisted. Creating a registration and clearing the Suggested Handle are atomic. A second registration is rejected, and suggestions never reserve handles.

All User HTTP responses, including signup, expose one shape with nullable `handle_registration` (`null` or `{ "handle": "…" }`) and nullable `suggestedHandle`. There is no identity-state discriminator or top-level handle. The Suggested Handle is retained for onboarding prefill and becomes null on successful registration. Central UI drives onboarding, home, and navigation from registration presence; session handling and identity-linking rules remain unchanged. A User obtains a Namespace only through their Handle Registration.

## Considered alternatives

- *Auto-link auth methods by email match* (Auth0 / Supabase defaults) — rejected as a documented account-takeover vector.
- *JWT tokens* — rejected because instant revocation is required (Visibility flips, PAT revocation, ownership changes must propagate immediately) and we have no federation use-case that would justify the operational cost (key rotation, JWKS, refresh + blocklist choreography). All comparable dev-tool registries (GitHub, GitLab, npm, crates.io, Docker Hub PATs, Stripe, Vercel) use opaque tokens for this reason.
- *PATs only* (original Docker Hub, crates.io) — rejected because day-one onboarding becomes "go to website, click around, mint a token, paste it" before the user has seen any value; device flow makes `ethoko login` work in one command.
- *Pre-login strict email verification* (AWS-style) — rejected as gratuitous friction; the canonical registry pattern is to gate writes, not logins.
